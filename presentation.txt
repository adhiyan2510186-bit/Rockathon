HOW TO USE THIS FILE
--------------------
This is not the deck and it is not documentation. It is the list of moments
where we hit a real problem in procurement, thought about it, and made a
deliberate choice - written as things to say out loud.

Judges do not reward features. They reward evidence that you understood the
problem well enough to make a call a naive build would never think to make.
Almost every entry below has the same shape:

    the trap  ->  what the obvious build does  ->  what we do  ->  the line

If you only memorise one thing per section, memorise THE LINE.

Companion files:
    EFFICIENCY.md - engineering claims (speed, cost, complexity), with file paths
    CLAUDE.md     - the rules the code obeys
    presentation.txt (this file) - domain judgement and pain points

Keep adding to this as we build. An entry earns its place if a judge could
plausibly ask "did you think about X?" and we want a real answer.


================================================================================
SECTION 0 - THE ONE LINE THAT FRAMES EVERYTHING
================================================================================

    "The LLM interprets language. It never decides the purchase."

Say this early and come back to it. Every design choice below is downstream of
it. If a judge remembers one sentence from us, this is the one.

The supporting fact, ready for the follow-up question:

    "Every number a judge could question - score, margin, limit check, ranking,
     urgency - is computed in plain Python from the same inputs every time.
     Our ranker is about sixty lines and it is unit-tested against the exact
     numbers on our slide. Same brief in, same ranking out, every run."

And the sharpest version, if they push on why that matters:

    "Our authorisation limit lives in a config file, not in a prompt. No
     phrasing inside a user's brief can talk the agent past it, because the
     agent never sees the limit as instruction. You cannot jailbreak a number
     the model was never shown."


================================================================================
SECTION 1 - READING WHAT A HUMAN ACTUALLY WROTE
================================================================================

1.1  THE SPACE THAT KILLS THE DEMO
    The trap:   Our parser returns "200x150x80 mm". The catalog says
                "200x150x80mm". Same box. One space apart.
    Naive:      String comparison fails, the box fails a NON-NEGOTIABLE spec
                gate, and the app shows zero eligible products for no visible
                reason. On stage that looks like the whole system is broken.
    We do:      Every spec is reduced to a comparable key - lowercase, no
                spaces, no punctuation - before comparison. Trade shorthand is
                expanded too: the aggregator writes "DW", the user writes
                "double-wall", the parser sometimes writes "double wall". All
                three have to mean one thing.
    THE LINE:   "We hit this for real while testing. A single space was failing
                 a hard constraint and hiding every product. Matching on
                 punctuation is how a procurement agent silently tells a buyer
                 'nothing exists' when the warehouse is full."

1.2  ONE QUESTION, NOT A FORM
    The trap:   Real briefs are incomplete. "I need mailer boxes" has no
                quantity, no cap, no deadline.
    Naive:      Either guess and start searching, or interrogate the user with
                a six-field form - which is just a form with extra steps.
    We do:      Stage 0 asks ONE targeted question about the field that
                actually blocks discovery. No search starts on a guess.
    THE LINE:   "An agent that guesses your budget and then shows you a ranked
                 list has made a purchasing decision on your behalf and hidden
                 it as a search result."

1.3  ASSUMED IS NOT CONFIRMED
    The trap:   The user never answers the clarifying question. We still need a
                number to proceed.
    Naive:      Fill in a default and carry on as though the user said it.
    We do:      Apply a declared default from config, and log it as ASSUMED -
                never CONFIRMED - at the moment it is applied, before discovery
                is allowed to use it.
    THE LINE:   "An assumption presented as an instruction is exactly the
                 failure an audit trail exists to prevent. Our log can always
                 tell you which numbers came from the buyer and which came
                 from us."

1.4  WE DEGRADE HONESTLY
    The trap:   The free API tier rate-limits at roughly ten requests a minute.
                A demo can die mid-run.
    Naive:      Hide it, or let the app crash on stage.
    We do:      Fall back to a deterministic offline parser, and the UI says so
                plainly.
    THE LINE:   "If the model is unreachable we switch to a deterministic
                 parser and we tell you we did. We degrade honestly. We never
                 fake a model call."


1.5  THE ADJECTIVE THAT WAS TREATED AS PART OF THE PRODUCT'S NAME
    The trap:   "25 wireless noise-cancelling headsets, over-ear, under Rs 4,000."
                Which of those words are requirements?
    Naive:      Whatever the model returns. Ours returned one: "over-ear", the
                word after the comma. It read "wireless noise-cancelling" as
                part of what the thing is CALLED rather than as two things the
                buyer requires.
    The cost:   Specs are a pass/fail gate. A missed spec is not a cosmetic loss
                - it is a product qualifying on something it does not have. A
                Rs 1,850 headset with no noise cancelling entered the pool for a
                buyer who had asked for noise cancelling, and it was the
                cheapest thing in it.
    We do:      The extraction prompt now says a word describing the item IS a
                spec, with a worked example in both category vocabularies. Live
                and offline parses now produce the identical eligible pool on
                all three demo briefs, which is the property we check.
    THE LINE:   "The model was not wrong about English - 'wireless
                 noise-cancelling headset' really is a product name. It was
                 wrong about our domain, where every adjective a buyer uses is a
                 requirement somebody has to meet. That is why the language step
                 is the only place a model touches, and why its output is
                 checked against a parser that cannot be persuaded."

1.6  A PREFERENCE DOES NOT HAVE TO NAME THE CRITERION
    The trap:   "5 gaming laptops - as cheap as possible - within 14 days."
    Naive:      Our extraction looked for a preference ATTACHED to a criterion
                ("reliability matters a lot") and came back with no priority at
                all. So the agent asked what the laptops were for, and the answer
                "development and builds" set price to 0.15 - the exact opposite
                of the one thing the buyer had actually said.
    Why it is worse than the spec bug: a missed spec ends in an honest refusal.
                A missed priority ends in a confident recommendation ranked
                against the buyer's own words, and nothing on the screen looks
                wrong.
    We do:      The extraction prompt now treats a superlative about the purchase
                as a stated priority - "as cheap as possible" is price at the
                strongest label, "we need these fast" is delivery. And stating a
                LIMIT is still not a preference: "max Rs 22 per unit" and "within
                10 days" are requirements, not priorities, or every brief would
                arrive pre-weighted by its own deadline.
    THE LINE:   "The dangerous parse is not the one that fails. It is the one
                 that succeeds while quietly dropping the only preference the
                 buyer expressed - and then asks them a question they already
                 answered."

================================================================================
SECTION 2 - TWO VENDORS, TWO SCHEMAS, ONE TRUTH
================================================================================

2.1  WE MADE THE DATA HARD ON PURPOSE
    The trap:   It is very tempting to write two mock catalogs with the same
                columns, because then "normalisation" is easy.
    Naive:      Two identical schemas. The normaliser is a rename. It proves
                nothing and a judge sees through it instantly.
    We do:      Deliberately incompatible feeds. Prices in PAISE vs rupees.
                Shipping as a RANGE vs a number. Vendor score out of 100 vs a
                rating out of 5. Returns as a SENTENCE vs an integer. Specs as
                a pipe-separated blob of trade shorthand vs a clean list.
    THE LINE:   "If both our feeds had the same columns, our normaliser would be
                 a rename and would prove nothing. Every one of those five
                 conversions is a place a real integration actually breaks."

2.2  THE PESSIMISTIC SHIPPING WINDOW  ** strong answer, expect this question **
    The trap:   The aggregator promises "7-9 days". Which number do you store?
    Naive:      Take 7. It is the first number in the string, and it makes more
                products pass the deadline.
    We do:      Store 9. Always the late end.
    Why:        A window is a promise about the earliest AND the latest date.
                A user's 10-day deadline is only genuinely met if the LATEST
                date clears it. Taking the 7 lets a product pass a hard gate on
                its best-case story.
    THE LINE:   "Promising a buyer seven days and delivering on nine is how a
                 supplier loses a customer. We plan against the date it might
                 actually arrive, not against its most flattering reading. It is
                 one function, deliberately, so it can be argued with."

2.3  WE TELL YOU WHAT WE CAN ACTUALLY BUY
    The trap:   Our config has default weights and a price cap for the "labels"
                category. No vendor in our catalogs stocks a single labels
                product.
    Naive:      List the categories from config. The agent then offers to buy
                things it cannot source.
    We do:      Read the available categories from the CATALOGS, not from
                config.
    THE LINE:   "Those are two different questions. Config knows what we have
                 opinions about; the catalogs know what we can actually buy. We
                 answer the buyer with the second one."

2.4  WE NEVER READ A SPEC OUT OF A PRODUCT TITLE  ** marketplace-specific **
    The trap:   A marketplace title carries the specs already. Amazon lists
                "Dell Inspiron 15 3520 15.6" FHD Laptop (12th Gen Core i5-1235U/
                8GB DDR4/512GB SSD/Win 11...)". Parsing "16GB" out of a string
                like that is thirty seconds of regex.
    Naive:      Read specs from the title. It works on most listings.
    We do:      Read spec_sheet, the structured field, and treat the title as
                display text only.
    Why:        Titles are advertising and they are wrong often enough that our
                own catalog carries a buyer complaining about it: "The listing
                photo showed 16GB. It is 8GB. Read the spec sheet, not the
                title." A gate that reads marketing copy inherits the marketing.
    THE LINE:   "The title is what the seller wants you to read. The spec sheet
                 is what they are willing to be held to. We gate on the second
                 one — and when they disagree, the user sees both."

2.5  THE SAME PRODUCT ON TWO SITES IS TWO OFFERS, NOT A DUPLICATE
    The trap:   The identical boAt Rockerz 550 is on Amazon at Rs 2,999 and on
                Flipkart at Rs 2,849 under a completely different title. The
                obvious thing is to de-duplicate them into one "product".
    Naive:      Fuzzy-match the titles, pick a canonical listing, drop the other.
    We do:      Rank both. Two rows, two prices, two delivery estimates.
    Why:        De-duplicating means silently discarding a real, purchasable
                offer on the strength of a string comparison. And the "duplicate"
                is not identical in the ways that matter: Flipkart is Rs 150
                cheaper and three days slower with a shorter replacement window,
                so it loses — visibly, on the terms the user set.
    THE LINE:   "We do not merge them, because they are not the same offer. The
                 cheaper one loses on delivery and replacement, and you can see
                 exactly by how much. A de-duplicator would have made that choice
                 for you and told you nothing."

2.6  A TYPO MUST NOT SILENTLY HALVE THE POOL
    The trap:   Source selection is a list of keys. A typo passes an unknown key.
    Naive:      Ignore unknown keys and return whatever matched.
    We do:      Raise immediately, naming the unknown source and the known ones.
    THE LINE:   "A typo that quietly drops one vendor would change our ranking
                 with no visible cause and no error. That is the one class of
                 bug an audit log cannot catch, because nothing wrong appears to
                 have happened."


================================================================================
SECTION 3 - RANKING: WHERE THE JUDGEMENT LIVES
================================================================================

3.1  THE CHEAPEST OPTION LOSES, AND THAT IS THE POINT
    The setup:  EcoMail is 20% under the price cap. It ranks LAST.
    Why:        The buyer said "reliability matters a lot - we got burned last
                quarter." Reliability contributed 0.450 of the winner's 0.580
                and 0.000 of EcoMail's 0.337.
    THE LINE:   "The formula has no favourite. The brief does. If she had said
                 price matters most, the same sixty lines would hand you
                 EcoMail - and we can show you that live."

3.1b THE BAD OPTION QUALIFIES, AND WE SHOW IT ANYWAY
     ** the answer to "what if the cheap one passes your filter?" - expect this **
    The setup:  The headsets brief. A Boult ProBass at Rs 1,299 - Rs 1,550 under
                the winner - passes EVERY hard gate. Over-ear, wireless, ANC, in
                stock, inside the cap, inside the window. It carries 2.8 stars
                and reviews saying the right cup died in a fortnight. It comes
                LAST, at 27.9 against the winner's 80.6.
    The trap:   Add a reliability floor to the filter. "Reject anything under
                3.5 stars." It feels responsible and it takes one line.
    Naive:      A hidden quality gate. The cheap option silently disappears and
                the buyer is never told there was a Rs 1,299 option at all.
    We do:      Nothing rejects on reliability. Reliability is a SOFT criterion,
                it only orders the list, and the Boult sits on screen in last
                place with its price advantage fully visible.
    Why:        A hard floor is us imposing our taste as a rule. The buyer might
                genuinely want the cheap ones for a warehouse floor. What she
                needs is the trade-off stated, not the option removed.
    THE LINE:   "We did not hide the cheap one. It passed every check we were
                 given. It lost by fifty-two points because she said reliability
                 mattered - and if she had said price mattered, the same sixty
                 lines would have handed it to her."

3.1c THE REVIEWS ARE ON FILE AND THEY SCORE NOTHING
     ** the LLM-temptation question in a new place **
    The trap:   Every marketplace listing carries thousands of words of buyer
                opinion. Feeding that to the model and asking "how good is this
                really?" is the single most demo-friendly thing in the dataset.
    Naive:      An LLM sentiment score folded into the ranking. It would look
                impressive for about ten seconds.
    We do:      Reviews travel with the product, are shown to the human under
                the score breakdown, and are read by nothing that decides
                anything. tests/test_reviews_are_advisory.py rewrites the
                winner's reviews into three furious one-stars and asserts the
                score does not move by a hair.
    Why:        Review text is unstructured, adversarial - sellers write some of
                it - and unreproducible. Three properties that would poison a
                number a finance manager has to defend in a meeting. The star
                RATING is different and IS scored, because it is already a
                number every source publishes the same way.
    THE LINE:   "The rating is a number, so we score it. The sentences are not,
                 so we show them to you instead. The difference between those two
                 is the entire project."

3.1d WE ASK WHAT THESE ARE FOR - AND ONLY WHEN WE HAVE NO ANSWER
     ** the interactive moment - this is the one to demo live **
    The setup:  "25 wireless noise-cancelling headsets, over-ear, under Rs 4,000,
                within 12 days." Complete brief. Every hard constraint stated.
                The scope gate has nothing to ask for. And it still does not say
                whether a dead headset costs a sales call or an afternoon of
                background music - which is the thing that decides the answer.
    The trap:   Two opposite failures, and most builds pick one. Either you
                never ask and quietly rank on your own house opinion, or you ask
                about everything and the agent becomes a form.
    Naive:      A wizard. Four questions before anything happens.
    We do:      ONE question, at stage 2, under two conditions that both have to
                hold: the category declares usage contexts in config.yaml, AND
                the user stated no priority in their own words. Three radio
                options, each with a line saying why it changes the answer.
    Why it is  The tag maps to a weight set in config.yaml. Python looks it up,
    still ours: exactly the way it looks up matters_a_lot -> 0.45. The LLM never
                sees a context, a weight, or this question.
    THE LINE:   "It asked because it did not know, not because it wanted to look
                 attentive. Watch: I pick 'kitting out new joiners' and the
                 runner-up changes - the boAt overtakes the AudioPro because it
                 arrives in three days instead of eight, and a new starter has a
                 start date. Same catalog, same sixty lines, different answer."

3.1e THE USER'S OWN WORDS ALWAYS BEAT OUR MENU
    The trap:   Now that we have a nice context dropdown, it is tempting to show
                it on every brief. More signal, better weights.
    Naive:      Always ask. The dropdown quietly overrides "reliability matters
                a lot" with whichever tag the user clicked.
    We do:      `context_needed()` returns None the moment a priority was stated.
                The menu exists for silence, not for disagreement.
    Why:        A buyer who typed what mattered has already answered. Replacing
                their sentence with our taxonomy is the same failure as letting
                the model decide - it is just wearing a nicer widget.
    THE LINE:   "If she told us what mattered, we never ask. Her words are a
                 better answer than our three buttons, and there is a test that
                 fails if the menu ever appears in front of a stated priority."

3.1f "NOT SURE" IS AN ANSWER, AND IT IS LOGGED AS AN ASSUMPTION
    The trap:   The question is now blocking. Nothing ranks until it is answered.
    Naive:      Force a choice. The agent sulks until you classify your own
                purchase, which is worse than having a default.
    We do:      A "Not sure - use your default" button. It applies the
                documented category weights and writes an ASSUMPTION to the
                audit log naming the question we asked and the options offered.
    Why:        Silence is never quietly converted into a preference. Same rule
                as every other unstated field: a declared default, logged as
                ASSUMED, never as CONFIRMED.
    THE LINE:   "Declining is a first-class answer. The log then says we asked,
                 she did not choose, and these are the weights we applied
                 instead. That is a different sentence from 'the buyer wanted
                 this', and the record has to be able to tell them apart."

3.1g WE STOP BEFORE RANKING, NOT AFTER
    The trap:   It is easier to rank with defaults, show the result, and offer a
                "refine" control underneath. Nothing blocks, nothing feels slow.
    Naive:      Rank first, re-rank on request.
    We do:      Stop at stage 2. Nothing is scored until the question is settled.
    Why:        This order is a correctness requirement, not a design taste. The
                headsets order is Rs 97,250 against a Rs 1,05,000 limit - INSIDE
                the agent's authority. Rank-then-ask means it would already have
                been confirmed and paid by the time the question appeared, and
                an agent cannot un-buy something because the buyer clarified
                their preference afterwards.
    THE LINE:   "We stop before we rank because this order is inside our spending
                 limit. If we had ranked first, we would have bought it first."

3.2  THE SQUARE ROOT
    The trap:   Score price by raw margin under the cap, and a deep discount
                dominates everything the buyer actually said.
    Naive:      Linear margin. A 20%-under bargain drowns out a stated priority.
    We do:      Score margins on sqrt(margin). Steep near the cap, flat far from
                it.
    Why:        It matches how buyers actually think. The first rupee under
                budget feels like a win; the twentieth barely registers.
    THE LINE:   "A bargain should not be able to shout down what the buyer told
                 us mattered. The square root is what stops that."

3.3  PRICE APPEARS TWICE AND IT IS NOT DOUBLE COUNTING
    Expect this question. It looks like a bug and it is not.
    Stage 3 asks:  "Is it under 22 rupees at all?"           -> eligibility
    Stage 4 asks:  "How far under, versus what else passed?"  -> preference
    THE LINE:   "Two different questions, one measurement, each used once.
                 Classification controls eligibility, not scoring. A product
                 that qualifies on price still has to earn its position on it."

3.4  WE ROUND THE WEIGHTS ON PURPOSE
    The trap:   Rescaling weights produces 0.1833333.
    Naive:      Show it. It looks precise and rigorous.
    We do:      Round to multiples of 0.05.
    THE LINE:   "A weight is a judgement about what someone cares about. Showing
                 an approver 'replacement: 0.1833' claims a precision we do not
                 have. Multiples of five percent are a number a human can argue
                 with - and an approver who cannot argue with a number is not
                 really approving anything."

3.5  WE KEEP THE REJECTIONS
    The trap:   Only the survivors matter, right?
    Naive:      Return the three that passed.
    We do:      Return all seven, each failure carrying a plain-words reason -
                "arrives in 12 days against a 10-day window, 2 days late".
    THE LINE:   "'Here are three products' is a claim. 'We looked at seven,
                 three qualified, and here is exactly why the other four did
                 not' is a checkable one. Those rejection reasons are also what
                 the escalation handler needs to build a near-miss list."


================================================================================
SECTION 4 - TIMING: ADVICE THAT KNOWS IT IS ONLY ADVICE
================================================================================

4.1  THE GUARDRAIL  ** this is our strongest single moment - rehearse it **
    The setup:  Our winner is flagged "Order today - about 3 days of cover
                left" AND it still stops and asks for human approval, because
                109,500 rupees is over our 105,000 authorisation limit.
    THE LINE:   "Urgency changes priority. It never changes authority. An agent
                 that can talk itself past its own spending limit by claiming
                 something is urgent is precisely the failure this project
                 exists to rule out."
    If pushed - and this is the good part:
                "It is structural, not a promise. The signals module imports
                 neither the ranker nor the authorisation check. It takes the
                 ranked list as read-only input and returns a separate object.
                 It has no way to write a score even if a future edit wanted it
                 to. We have a test that runs the pipeline with signals and
                 without and asserts the decision is identical, and another that
                 fails if anyone ever adds those imports."

4.2  DAYS OF COVER FOR *YOUR* ORDER, NOT DAYS TO ZERO
    The trap:   "Stock cover" sounds obvious: stock divided by burn rate.
    Naive:      Report days until the vendor hits zero. Corusafe: 4 days.
    We do:      Report days until stock falls below THIS buyer's quantity.
                Corusafe: 3 days.
    THE LINE:   "A vendor with 20,000 units hits zero in four days, but they can
                 no longer fill her 5,000-unit order in three. Measuring to zero
                 reports the flattering number and quietly makes the whole
                 signal useless for exactly the buyer it is meant to help."

4.3  TWO READS, NEVER AVERAGED
    The trap:   Stock says urgent, price says relax. Combine them?
    Naive:      Average the two into one score.
    We do:      Take the more urgent, and always name which one drove it.
    THE LINE:   "Average them and a falling price hides a stock cliff. We would
                 rather show you two facts than one number that lost both."

4.4  A SIGNAL THAT FIRES ON NOISE IS WORSE THAN NO SIGNAL
    The trap:   Every price moves a little.
    Naive:      Report every movement as a trend. Everything looks urgent.
    We do:      A 3% materiality threshold, in config. Below it we say "steady"
                and claim nothing.
    THE LINE:   "If everything is urgent, nothing is. A signal that fires on
                 noise trains a buyer to ignore it, which is worse than not
                 having built it."

4.5  NO HISTORY MEANS WE SAY NOTHING
    The trap:   A source publishes no price history.
    Naive:      Extrapolate from one point, or show a neutral-looking default.
    We do:      Return "unknown" and make no claims at all.
    THE LINE:   "A source that tells us nothing should produce silence, not a
                 confident-looking guess. Refusing to answer is a feature."

4.6  RESTOCKING IS NOT AN EMERGENCY
    The trap:   Stock going UP produces a negative depletion rate, and a
                negative "days of cover" renders as an alarming number.
    We do:      Detect it explicitly and report "stock steady or rising".
    THE LINE:   "We check for it, because an arithmetic artefact that looks like
                 a red warning is how a buyer stops trusting the whole panel."

4.7  WE ANCHOR TO THE FEED, NOT THE WALL CLOCK
    The trap:   Compute "days of cover" from today's date.
    Naive:      Use date.today(). Obvious, and it silently rots.
    We do:      Anchor every calculation to the last observation date in the
                feed.
    THE LINE:   "If we used today's date, the same catalog would say something
                 different tomorrow, our locked test numbers would break
                 overnight, and a demo in another timezone would disagree with
                 this one. Determinism is what we are selling. It does not get
                 an exception because a feature was convenient."

4.8  OUR CHARTS SAY THEY ARE SIMULATED
    The trap:   A convincing price-history chart implies a real market feed.
    Naive:      Draw it and let the judge assume.
    We do:      Label every chart "simulated market data", and carry that fact
                into the audit log itself.
    THE LINE:   "This is authored demo data and we say so on the screen and in
                 the log. Drawing a convincing chart and letting you assume it
                 was real would contradict the exact property - an auditable
                 agent - that we are asking you to believe in."

4.9  A BADGE ON TWO ROWS TELLS YOU NOTHING
    We do:      "Cheapest that qualified" is awarded only to a strictly unique
                winner. On a tie, nobody gets it.
    THE LINE:   "'Joint cheapest' is not a distinguishing fact."


================================================================================
SECTION 5 - WHERE THE AGENT'S AUTHORITY ENDS
================================================================================

5.1  TWO LIMITS, NOT ONE  ** commonly confused - be crisp **
    Per-unit cap (22 rupees):        a HARD constraint, enforced at stage 3.
                                     Nothing above it is ever considered.
    Authorisation limit (105,000):   total spend the agent may commit ALONE,
                                     enforced at stage 5. Exceeding it
                                     ESCALATES.
    THE LINE:   "One controls what it may buy. The other controls what it may
                 buy WITHOUT US. Conflating those two is how autonomous agents
                 end up either useless or terrifying."

5.2  OVER THE LIMIT IS NOT A REJECTION
    THE LINE:   "The agent never refuses an order for being expensive. It
                 declares that this one is above its own pay grade. There is
                 deliberately no third outcome called 'rejected'."

5.3  SILENCE IS NEVER APPROVAL
    The trap:   A pending approval nobody answers.
    Naive:      Time out and proceed, or time out and cancel everything.
    We do:      The request expires. Transaction state is preserved, so
                approving later resumes at vendor confirmation - it does not
                re-run discovery.
    THE LINE:   "Silence is never approval. And approving twenty minutes later
                 does not mean starting over - we resume exactly where the human
                 was asked."

5.4  THE FIVE-POINT SUBSTITUTION THRESHOLD
    The trap:   The winner becomes unavailable at confirmation. Just take #2?
    Naive:      Silently swap. The user never learns their pick changed.
    We do:      Swap only if the gap is 5 points or less. In our demo the gap is
                9.3, so the agent escalates instead.
    THE LINE:   "A wide gap means number two is a meaningfully worse fit for
                 what she actually asked for. Silently swapping is how an agent
                 buys something the buyer never chose and calls it a fallback."

5.4b  A REFUSAL THAT DOES NOT NAME THE REASON IS NOT AN ANSWER
    The trap:   Nothing qualified, and every miss was on a requirement we never
                relax. There is genuinely nothing to offer.
    Naive:      Say so. Ours said "the gaps are on category, quantity or
                specification, which we do not relax" - which is true, complete,
                and useless. A buyer who typed "5 gaming laptops" is told the
                SHAPE of the problem and left to guess its content.
    We do:      Name the requirement that blocked the whole pool, in the buyer's
                own words: "we checked 16 laptops and none of them clears every
                requirement - nothing we can source lists 'gaming'." Only a
                requirement that blocked EVERY product is named; a spec two
                products lack is not why the search failed, and blaming it sends
                someone off to fix the wrong word.
    Note:       The reason is read back off the violation the filter already
                wrote, not recomputed. If the screen and the log ever disagreed
                about why nothing was bought, the log stops being evidence.
    THE LINE:   "We had the exact word that killed the search on all sixteen
                 rows and we were showing none of them. A refusal is a product
                 surface too - 'no' without 'because' is where a user decides
                 the tool is broken."

5.5  WHAT IS DELIBERATELY *NOT* AN ESCALATION  ** shows restraint - use it **
    The trap:   The top pick is imperfect on some soft preference.
    Naive:      Escalate to be safe.
    We do:      Nothing. Ranking already absorbed it.
    THE LINE:   "Escalate on that and every order escalates, which erases the
                 exact boundary we are demonstrating. Knowing what NOT to ask a
                 human about is as much of the design as knowing what to."

5.6  ONE ESCALATION HANDLER, FOUR DOORS
    We do:      One mechanism - detect, re-validate, relax, re-rank, escalate -
                entered from four places: no eligible match, over limit,
                unavailable at confirmation, payment failed twice.
    THE LINE:   "Four separate code paths would drift apart, and the one that
                 drifts is the one that quietly stops logging."

5.7  NON-NEGOTIABLE VS NEGOTIABLE
    We do:      Price, delivery and minor spec gaps may be PROPOSED for
                relaxation. Category, quantity and safety specs never are.
    THE LINE:   "Ordering 5,000 boxes and receiving 500 is not a near-miss. And
                 even a negotiable limit is only ever proposed - never applied
                 silently."


================================================================================
SECTION 6 - NOT TRUSTING OURSELVES
================================================================================

6.1  WE REFUSE TO CACHE THE ONE THING IT WOULD BE EASY TO CACHE
    ** this is our best engineering answer - it shows we thought, not just built **
    The trap:   We cache both catalogs after the first read. Obvious win.
    The bug it would have caused: stage 6 re-validates price and stock before
                paying. If that read came from cache, we would be comparing our
                own copy against our own copy.
    We do:      Stage 6 forces a genuine re-read. It is the ONLY caller that
                does.
    THE LINE:   "We cache aggressively everywhere except the one place where
                 caching would be a correctness bug. Re-checking a cached copy
                 against itself passes every single time - that is not a check,
                 it is a formality."

6.2  WE NEVER TRUST OUR OWN SORT ORDER
    We do:      A fallback product is re-validated independently against the
                hard gates before it is offered - using the same filter stage 3
                used, not a quick check written for the occasion.
    THE LINE:   "Being second on a list is not the same as being eligible. The
                 pool was ranked before the world changed."

6.3  VANISHED AND SOLD OUT ARE THE SAME FACT
    We do:      A product that disappears from the catalog between discovery and
                confirmation comes back as a zero-stock version of itself.
    THE LINE:   "'The vendor no longer lists it' and 'the vendor has none' are
                 the same fact to a buyer. Routing both through the stock gate
                 means one failure path instead of two - and two failure paths
                 is how one of them ends up untested."

6.4  OUR OWN DEMO DATA CANNOT CONTRADICT ITSELF
    We do:      A test asserts the last point of every price and stock history
                equals the product's current price and stock.
    THE LINE:   "That is the drift that creeps into authored data the moment
                 someone edits one number and forgets the other - and it would
                 make every signal we compute meaningless."

6.4b  OUR "NO NETWORK" TESTS WERE ON THE NETWORK, AND PASSED ANYWAY
    ** the best bug we found, because of the SHAPE of it **
    The trap:   The test suite clears GEMINI_API_KEY to force the deterministic
                offline parser. Every file says so in its docstring.
    The bug:    An empty string is falsy. `_api_key()` saw no usable value in the
                environment and fell through to reading .env off the disk - so
                the "offline" tests were calling the real model, on every run.
    Why nobody noticed: they passed. The free-tier quota was exhausted, so every
                call came back 429 and dropped to the offline parser, which is
                exactly what we were asserting against. Two things were broken
                and each one hid the other. It surfaced only when we moved to a
                model with quota left: a live parse came back, read one brief
                differently, and a test that had never failed went red.
    We do:      An explicitly empty key now means "no key" and stops there, and
                a test asserts the promise directly rather than restating it in
                a docstring (test_the_offline_fixture_actually_forces_offline).
    Measured:   The suite went from ~120 seconds to 16. That was the network.
    THE LINE:   "Our offline tests were quietly online for weeks and passed
                 every time, because our API quota was exhausted and the failure
                 mode we were testing was the failure mode we were accidentally
                 in. A green test is not evidence until you know what would have
                 turned it red."

6.5  THE GOLDEN NUMBERS
    We do:      58.0 / 48.7 / 33.7 are asserted by a unit test that runs the
                real pipeline with no API key and no network.
    THE LINE:   "Those three numbers are on our slide. If our code ever
                 disagrees with our deck, the test goes red on a laptop instead
                 of on stage. The test IS the deck."


================================================================================
SECTION 7 - THE AUDIT TRAIL IS THE PRODUCT
================================================================================

7.1  WRITTEN AT THE MOMENT, NOT RECONSTRUCTED AFTER
    Naive:      Assemble a decision trail at the end from final state. Much
                easier to write.
    We do:      Every entry is appended the instant the event happens, and
                flushed to disk immediately.
    THE LINE:   "An assumption logged after the purchase is just a story. We
                 write it before discovery is allowed to use it."

7.2  IT ANSWERS A FINANCE MANAGER'S FOUR QUESTIONS
    WHAT happened  - the event type, in plain words
    WHY            - one sentence, not a stack trace
    WHAT WE DID    - the action, or explicitly "no purchase executed"
    WHO NEEDS TO KNOW - a notify list that drives the finance email
    THE LINE:   "One transaction id replays the entire order in sequence without
                 reading a line of our code."

7.3  ADVICE IS NOT A MONEY EVENT
    We do:      Market signals notify the requester only. Escalations notify
                finance too.
    THE LINE:   "Finance needs to hear when money is about to move, not when a
                 vendor is running low on cardboard. Copying them on advice is
                 how a notify list becomes noise nobody reads."

7.4  THE LOG SAYS EXPLICITLY THAT ADVICE CHANGED NOTHING
    We do:      Every market-signal entry carries "advisory only - ranking and
                authorisation unchanged".
    THE LINE:   "An entry that merely notes 'stock is low' invites a later
                 reader to wonder whether it tipped the decision. We close that
                 question inside the log itself."

7.5  ONE RECORD, TWO EXPORTS
    We do:      JSONL for systems, a one-page rendered view for a human auditor
                - from the same record.
    THE LINE:   "Not two logs that can disagree. One record, read two ways."


================================================================================
SECTION 8 - WHAT WE CHOSE NOT TO BUILD, AND WHY THAT IS A STRENGTH
================================================================================

Name these before a judge finds them. Volunteering a limit reads as command of
the problem; being caught by one reads as the opposite.

8.1  MOCK VENDORS
    "Mock vendors hide real integration pain - auth, rate limits, pagination,
     downtime. We are not going to pretend two local files are an integration.
     What we did build is the seam: every source is an adapter behind one
     interface, so a live vendor API is one new file and nothing else changes.
     The source toggle you just watched is that seam, working."

8.2  NO CROSS-BRIEF OPTIMISATION
    "Briefs are priced independently. Real bundle discounts across simultaneous
     orders are a genuinely harder problem and we would rather name it than fake
     it."

8.3  "NEGOTIATION" IS CONFIRM-AND-LOCK
    "We re-validate and lock a price. We do not bargain. Calling that
     negotiation would be overclaiming."

8.4  OUR DEFAULT WEIGHTS ARE A JUDGEMENT CALL
    "The category defaults are our opinion. They are documented in config and a
     user can edit them - which is the honest position, because there is no
     objectively correct weight for 'replacement window' and anyone who tells
     you otherwise is guessing too."

8.5  RELAXATION ORDER NEEDS A HUMAN SIGNAL
    "If the buyer has not told us which limit they would bend first, we fall
     back to smallest-violation ordering and we surface it rather than acting on
     it. We are not going to infer someone's flexibility from silence."


================================================================================
SECTION 8.5 - THE INTERFACE: DESIGN DECISIONS THAT ARE ACTUALLY ENGINEERING
================================================================================

8.5.1  WE TOOK THE EXPLANATION OFF THE SCREEN AND PUT IT IN OUR MOUTHS
    The trap:   Our own reasoning is the best thing about this project, so the
                temptation is to print all of it, all the time.
    Naive:      Captions everywhere. "Stage 4 - ranked, pure Python, same brief
                in, same order out." It reads as a slide, not a product, and a
                buyer skips every word of it.
    We do:      Clean surface, and every piece of reasoning one click away in a
                drill-down. Progressive disclosure.
    THE LINE:   "The reasoning is our whole thesis, so we did not delete it - we
                made it earned rather than shoved. Watch what happens when I ask
                the product WHY." (open the score breakdown)
    Why it is better on stage: a judge watching you OPEN the arithmetic on
    request is far more convincing than a judge skim-reading it in a wall of
    captions they never asked for.

8.5.2  WE HAVE A TEST THAT FAILS IF WE START EXPLAINING OURSELVES AGAIN
    The trap:   "Clean UI" is a rule that erodes one helpful caption at a time.
    We do:      tests/test_app.py::test_no_pipeline_vocabulary_on_the_surface
                drives the real app and fails if "stage 4", "pure Python",
                "normalise", "hard gate" or a dozen other terms appear on the
                default screen. Drill-down contents are deliberately exempt.
    THE LINE:   "We turned a design rule into a failing test, because a design
                rule nobody enforces is a preference."

8.5.3  WE DID NOT PICK OUR CHART COLOURS
    The trap:   Choose four colours that look distinct TO US.
    Naive:      Exactly that. It is how roughly one in twelve men - quite
                possibly someone on the panel - ends up unable to read your
                chart.
    We do:      Use a published, pre-validated categorical palette unchanged and
                in its documented order, so adjacent series clear real
                colour-vision-deficiency separation thresholds. Our line charts
                plot at most three products, because only the first three slots
                clear the stricter all-pairs gate.
    Also:       Two of the four slots are low-contrast on a light background. The
                documented mitigation is visible direct labels or a table view.
                We ship both, on the same screen.
    THE LINE:   "We treated accessibility as a constraint with numbers in it,
                not as a nice-to-have. Colour never carries meaning alone
                anywhere in this app."

8.5.4  WE PINNED THE THEME, AND THEN WE PINNED IT IN ONE PLACE
    The trap:   Streamlit follows whatever laptop it is running on, so the
                interface a judge sees is decided by a setting on a machine we
                have never touched.
    Naive:      Declare both a light and a dark theme and let the viewer's OS
                choose. It reads well in a config file. It means we do not know
                what the demo looks like until we are standing in front of it.
    We do:      One theme, declared once, in .streamlit/config.toml. Dark.
    The bug we hit: we had our own stylesheet reading `st.context.theme.type`
                while Streamlit painted its widgets from config. Those are two
                different questions - "what does this browser prefer?" and "what
                theme is this app painted in?" - and on a light-mode laptop they
                gave two different answers. The page came out half dark chrome
                and half light cards. Both halves were individually correct.
    The fix:    ui/theme.py:active() now reads the same `theme.base` line
                Streamlit reads. One source, one answer.
    THE LINE:   "The palette was validated against the surface it is drawn on,
                so the surface is not allowed to be a surprise. And when we found
                our stylesheet and Streamlit disagreeing about which mode we were
                in, we did not add a third setting to reconcile them - we deleted
                one of the two sources. Two places that both decide the same
                thing is not redundancy, it is a bug waiting for a demo."

8.5.5  TWO CHARTS, NEVER ONE WITH TWO Y-AXES
    The trap:   Price and stock over the same dates. Obvious to overlay.
    Naive:      A dual-axis chart. It looks sophisticated.
    We do:      Two separate charts.
    THE LINE:   "With two y-scales you can manufacture any correlation you like
                by choosing the scales. Two charts cannot lie that way. It is the
                single most common way a dashboard misleads the person reading
                it."

8.5.6  THE STOCK CHART HAS THE BUYER'S OWN NUMBER DRAWN ACROSS IT
    We do:      A dotted reference line at the order quantity - "you need 5,000".
    THE LINE:   "Stock falling is mildly interesting. Stock falling TOWARD the
                line you need is a date. That crossing is the fact our timing
                engine computes, and here it is drawn rather than asserted."

8.5.7  AN ESCALATION IS NOT AN ERROR, SO IT IS NOT RED
    The trap:   Being asked to approve something is an interruption, so colour it
                like a warning.
    We do:      The approval card is the same shape as the recommendation card in
                a different key. No alarm banner.
    THE LINE:   "Being asked to approve a large order is the system working
                exactly as designed. Colouring it like a failure teaches the user
                to dread the one moment we are proudest of."

8.5.8  COLOUR FOLLOWS THE CRITERION, NEVER THE RANK
    We do:      Reliability is blue whether it is the biggest contribution or
                zero. A product keeps its colour when the pool changes.
    THE LINE:   "If colours got reassigned by rank, every filter change would
                repaint the chart and the reader would lose the thread mid-demo."

8.5.9  WE SPLIT ONE 819-LINE FILE INTO A LAYER THAT CANNOT DECIDE ANYTHING
    We do:      ui/theme.py, ui/charts.py, ui/components.py, and an app.py that
                only holds state and calls the engine. The UI reads objects the
                engine already produced and computes nothing.
    THE LINE:   "If a number on screen could be computed in the interface, it
                could disagree with the audit log - and then we would have two
                answers to one question. The log is supposed to be the answer, so
                the screen is not allowed to do arithmetic."


8.5.10  DARK MODE IS SELECTED, NOT FLIPPED
    The trap:   "Add dark mode" sounds like inverting the lightness.
    Naive:      Flip the palette. Every accessibility gate it passed on white
                quietly fails on black - contrast against the surface changes,
                and so does the separation between adjacent series.
    We do:      The dark column is the SAME eight hues re-stepped for a dark
                surface and validated as a set against it. Streamlit's chrome is
                themed from the same values in .streamlit/config.toml, and
                ui/theme.py reads theme.base back from that one file so our
                cards and our charts agree with the widgets around them. It is
                declared once, in config, not read off the viewer's machine -
                see 8.5.4 for why that distinction cost us a rehearsal.
    THE LINE:   "Our dark mode is a second validated palette, not an inversion.
                 A palette that passed every contrast gate on white will fail
                 all of them on black if you just flip it."

8.5.11  WE DELETED A LINE OF CONFIG THAT THEMED NOTHING
    We do:      Streamlit has a chartCategoricalColors option. We drew all three
                charts ourselves, so it themes nothing we ship - and it does not
                exist per-mode, which ours must. So it is not in our config.
    THE LINE:   "Config that looks like it does something and does not is worse
                 than no config, because the next person trusts it."

8.5.12  THE SUPPLIER BADGE GOT ITS OWN COLOURS, NOT THE CHART'S
    The trap:   Suppliers should be colour-coded - Amazon, Flipkart, PackHub
                should be tellable apart at a glance. Four validated hues are
                already sitting in the palette. Use those.
    Naive:      Exactly that, and it quietly breaks the rule the whole palette
                rests on. Blue means "reliability" everywhere in this app. A blue
                Amazon badge beside a blue reliability chip makes one colour mean
                two things, and then it means nothing.
    We do:      A separate small ramp for supplier identity (ui/theme.py,
                vendor_colour), deliberately outside both the four series hues
                and the four status hues, and used only on a badge mark - never
                in a chart, so it can never be read as a data series. The colour
                is assigned by the supplier's position in the source list, so a
                new adapter picks up a colour with no UI change and two suppliers
                cannot collide.
    Also:       The badge always carries the NAME and the kind of supplier
                ("Direct vendor" / "Marketplace") in words. Same rule as the
                urgency chips: colour never carries the meaning on its own.
    THE LINE:   "Colour-coding the vendors was the obvious ask, and the obvious
                 way to do it would have made our chart palette ambiguous. A
                 colour that means two things means nothing, so supplier identity
                 got its own ramp and stays off the charts entirely."

8.5.13  THE SPEC BADGES SAY WHICH SPECS DID THE QUALIFYING
    The trap:   Print the supplier's spec list. It looks complete.
    Naive:      A flat row of chips - "double-wall, kraft, 200x150x80mm" - where
                the buyer cannot tell which of those they actually asked for and
                which the supplier simply happens to list.
    We do:      Ticked, solid badges for the specs the brief required; dashed,
                quiet ones for everything else. The match is the same set
                membership the eligibility check uses, so a tick on screen can
                never disagree with the reason the product qualified.
    THE LINE:   "Two states, because they answer different questions: this is why
                 the product is on your screen, and this is what else you get."

================================================================================
SECTION 8.8 - MORE THAN ONE KIND OF PURCHASE
================================================================================

8.8.1  THE TRAP: A SECOND CATEGORY THAT IS STILL HARDCODED
    The obvious build: copy the packaging path, add a furniture catalog, and put
    `if category == "furniture"` wherever the two differ. It works. It demos.
    And the first judge who asks "what about a fourth category?" gets an answer
    that costs another day of work each time.

    What we do: a category is ONE BLOCK in config.yaml, carrying its price cap,
    its default weights, its trigger keywords, its spec vocabulary and its trade
    shorthand. No file in agent/ contains a category name at all - except
    config.py, whose whole job is reading those blocks.

    THE LINE: "Scroll to the furniture block. That is the entire furniture
    implementation - no code, no branch, no new path through the ranker. And
    there is a test that reads every module in agent/, strips the comments, and
    fails if anyone hardcodes a category name."

8.8.2  THE TRAP: THE DEMO ONLY EVER SHOWS THE AGENT REFUSING
    Our packaging order is over the authorisation limit, so it always stops for
    approval. That proves the agent knows where its authority ends - but an
    agent that ALWAYS stops has not demonstrated authority, only caution. A
    judge cannot tell the difference between a careful agent and a broken one
    that escalates everything.

    What we do: the three categories land in deliberately different places.
    Chairs cost Rs 78,000 against a Rs 1,05,000 limit, so the agent buys them
    and reports afterwards. Laptops cost Rs 4,64,000, so it stops. Same engine,
    same screen, opposite branch.

    THE LINE: "Watch it buy the chairs without asking. Now watch the same code
    refuse the laptops. The boundary is not a screen we wrote - it is one
    comparison against one number in a config file."

8.8.3  THE TRAP: A PRICE CAP WITH A COMMA IN IT
    A bug we actually hit. Our price matcher read digits as `[\d]+`, which is
    correct for "max Rs 22" and silently wrong for "max Rs 65,000" - it stops at
    the comma and returns a cap of sixty-five rupees. Every laptop then
    "exceeds" it, the pool empties, and the screen blames the vendors for a bug
    in our regex. Nothing crashes, which is what makes it dangerous.

    What we do: the same comma-grouped pattern the quantity matcher already
    used, and a test that asserts the parsed cap for both briefs.

    THE LINE: "Our packaging demo never had a comma in a number. That is exactly
    the kind of assumption a second category finds for you - which is half the
    reason we added one."

8.8.4  THE TRAP: THE QUESTION A USER CANNOT ANSWER
    Ask for cement. The keyword parser has no vocabulary for it, so it returned
    a blank category - and blank means "you did not say what you are buying", so
    the scope gate asked. The user answers "cement". Still blank. It asks again.
    Forever, with no hint that the real problem is that nobody stocks cement.

    What we do: when no keyword matches we keep the user's own words. The brief
    then reaches stage 3, finds nothing, and the no-coverage path names the
    categories we can actually source - which is the answer they needed three
    questions ago.

    THE LINE: "The honest failure is not 'no results'. It is 'I buy packaging,
    furniture and laptops, and cement is not one of them.' A search box says the
    first. An agent should say the second."

8.8.5  WHAT WE DID NOT MAKE CONFIGURABLE, AND WHY
    The four soft criteria - reliability, price, replacement window, delivery -
    are the same in every category and cannot be changed per category. That was
    a choice, not an oversight: they are the universal commercial questions, and
    a replacement window IS a warranty on a chair or a laptop. Making them
    per-category would have meant editing the ranker, the weight engine, every
    weight table and the chart palette, in exchange for nothing a buyer notices.

    THE LINE: "Specs are what differ between categories. Buying criteria are
    not. A chair and a box are compared on the same four questions, which is why
    one ranker serves all three."


8.8.6  THE TRAP: EVERY BRIEF WE WROTE OURSELVES STARTS WITH THE NUMBER
    A bug a user found in ten seconds. All five briefs in our own tests are
    shaped "5,000 kraft mailer boxes" - quantity first, product second - so the
    parser learned to read the product as "the words after the number". Then
    someone typed "Buy me latex gloves under 50 each arriving in 12 days".
    Product first. The parser walked past the gloves entirely and reported the
    category as "each arriving in not more than".

    Two more faults were hiding behind it. "50 each" was a price with no
    currency symbol, so our cap matcher - which wanted "Rs" or a word like
    "max" - missed it, left the 50 in the sentence, and the quantity matcher
    took it. The agent had quietly turned a Rs 50 ceiling into an order of
    fifty. Nothing crashed. No audit entry was wrong. The screen looked normal.

    What we do: the cap matcher accepts a bare number when "each" or "per unit"
    follows it immediately - which no quantity in a real sentence ever does. And
    the category falls back to the words after the number OR the words before
    it, cut at the first word that starts talking about the deal instead of the
    goods ("under", "each", "delivered", "within"). With the price correctly
    read as a price, the brief now has no quantity at all - so the scope gate
    asks the one question it should have asked from the start.

    THE LINE: "Our test briefs were all written by us, so they were all shaped
    like us. The first real sentence a stranger typed found three bugs at once,
    and the worst of them read a price as a quantity - the kind that does not
    crash, does not log an error, and just buys the wrong amount. That is why
    the parse is now in the test suite in both word orders."


8.8.7  WE ONLY ASK WHERE THE ANSWER ACTUALLY MOVES THE RANKING
    The trap:   The usage question is our best interaction, so put it on every
                category.
    Naive:      Every category gets a menu. Most of the answers land on weight
                sets close enough that the ranking never changes - and now the
                agent asks a question, makes the buyer stop and think, and
                produces the same recommendation whatever they pick. That is a
                widget that makes an agent look attentive and changes nothing.
    We do:      Contexts are opt-in data. A category declares a question only
                when we have checked that the answers reorder the real pool. We
                ran the laptop pool under all three candidate weight sets before
                shipping the block, and kept it because it flips the WINNER:
                "development and builds" picks the DevBook, "out on the road"
                picks the CoreStation on its 45-day replacement window against
                the DevBook's 30. Packaging still declares none - a box is a box.
    Cost:       A config block. No new branch, no new code path, no Python at
                all - which is the "a category is data, not code" claim being
                spent rather than asserted.
    THE LINE:   "Adding that question to laptops was ten lines of config and no
                 code. We checked first that the answer actually changes the
                 recommendation - tell it these go out on the road and a
                 different machine wins, on the longer replacement window. If it
                 had not moved the ranking we would not have asked, because a
                 question that cannot change the answer is just friction."


8.8.8  THE TRAP: EVERY WAY OF SAYING "NO" IS BUILT OUT OF THE WORD "YES"
    We tested our parser on briefs that told it what to care about. Nobody had
    tested one that told it what NOT to care about. So we typed "40 headsets,
    over-ear, within 12 days. Don't care about price."

    The parser scored price UP. It scanned the clause for strength words, found
    "care about" sitting inside "don't care about", and recorded price as
    mattering - on that category, a rise from the 0.25 default to 0.30. The
    agent had taken the one instruction the buyer gave it and applied its
    opposite. Nothing crashed, no gate misfired, and the approval screen printed
    a confident weight next to the word "user-stated".

    The deeper fault was that we could not have got it right even in principle.
    Our phrase table had three labels and the weakest was nice_to_have at 0.15,
    so there was no value in the system that meant "this criterion should not
    count". A dismissal had nowhere to land.

    What we do: a fourth label, does_not_matter, at 0.00 in config.yaml - and it
    is the only weight allowed to be zero, which the config validator now says
    out loud. Then the offline parser checks negation cues BEFORE any strength
    phrase, because that ordering is the whole fix: in English every dismissal
    is an endorsement with a "not" in front of it, so a matcher that looks for
    endorsements first will always read them backwards. The Gemini prompt learnt
    the same rule, and we checked both paths return does_not_matter on the same
    sentence.

    Zero is the honest number. It does not mean we ignored the criterion; it
    means the buyer removed it, and the score breakdown shows a 0.00 next to
    "user-stated (does not matter)" rather than hiding it.

    THE LINE: "Ask it for the cheapest option and it works. Tell it you don't
    care about price and it used to make price matter MORE - because the words
    'care about' are inside 'don't care about'. Every way of saying no in
    English is built out of the word yes. We check the negation first now, and
    we added a weight of zero, because until we did there was no number in the
    system that meant 'the buyer took this off the table'."


8.8.9  THE TRAP: WE INVENTED A NUMBER AND THEN ENFORCED IT
    Type "40 headsets, over-ear, within 12 days" - a complete, buyable brief -
    and the agent used to silently throw away every headset over Rs 5,000.

    That ceiling came from our config file. The buyer never said it, never saw
    it, and could not argue with it. And we knew it was a guess: stage 1 already
    marked the field ASSUMED and wrote an audit entry saying so. Then stage 3
    read the value, ignored the mark, and used it as a pass/fail gate. The pool
    came back thin and the screen blamed the vendors.

    Naive: a price cap is a hard constraint, so apply it. It is in the config,
    so it must be the policy.

    What we do: the filter reads the provenance flag it was already writing. A
    stated ceiling still excludes products above it. An assumed one excludes
    nothing - price falls through to stage 4 and is SCORED instead, so expensive
    costs a product points rather than its place in the pool. The chip on screen
    says "no price ceiling given" instead of printing a limit we made up, and
    the audit entry records price_gate_applied: false so the log never claims a
    check that did not run.

    Nothing gets bought recklessly as a result: with no ceiling, an expensive
    winner pushes the order total past the authorisation limit and stage 5
    escalates to a human. The safety net is the limit, which is real - not the
    guess, which was not.

    THE LINE: "We were already recording that the price cap was our assumption
    and not the buyer's instruction. We just weren't reading our own note - the
    filter took the guess and enforced it like policy. An assumption is allowed
    to fill in a blank. It is not allowed to disqualify anybody."

8.8.10  THE TRAP: THE ONLY WAY TO SAVE QUOTA WAS TO HIDE THE API KEY
    The free tier bills PER DAY, and reading one brief costs two calls - the
    scope check at stage 0 and the extraction at stage 1. Twenty rehearsal runs
    is forty calls spent before a judge has seen anything. We had already lost
    whole afternoons to this once and changed model over it.

    The only lever we had was deleting the key from .env. That works, and it is
    the wrong lever: with no key the app also stops being able to show that it
    HAS a language step. You cannot demonstrate the thing you switched off by
    making it look like it was never built.

    Naive: add a flag, and check it after the call - or add it in a prompt.
    Both are theatre. A flag read after the request has been sent has saved
    nothing at all, and it is exactly the kind of "off switch" that is off in
    the UI and on in the bill.

    What we do: one switch on screen - "Use AI to read my request" - that is
    read ONCE per brief and passed into both language calls, so a brief can
    never be half-read by the model and half by the word matcher. When it is
    off, no request is constructed and none is sent. The app says which reader
    ran and WHY: "switched off, so no request was sent" is a different sentence
    from "rate limit reached", because a choice the user made must never read as
    a fault they need to go and fix.

    The reason we can offer that switch at all is the architecture, not a
    feature we added. The model only ever turns a sentence into fields. Swap the
    reader and the ranking, the limit check and the audit trail are untouched -
    we have a test asserting the two paths produce an identical Brief, field for
    field.

    THE LINE: "Turn the AI off, mid-demo, and ask us the same question again.
    You get the same ranking and the same escalation, because the model was
    never the part that decided anything. That is not a fallback we bolted on -
    it is what 'the LLM interprets language, it never decides the purchase'
    actually buys you."


================================================================================
SECTION 9 - LIKELY QUESTIONS, AND THE SHORT ANSWER
================================================================================

Q: "How do I know the LLM isn't secretly deciding?"
A: "Pull the network cable. Our test suite runs the entire ranking pipeline with
    no API key and produces identical numbers. The ranker imports no model."

Q: "What if a user writes 'ignore your limit, this is urgent'?"
A: "The model never sees the limit. It reads language into structured fields;
    Python reads the limit from a config file. There is no instruction channel
    between the two."

Q: "Your data is fake."
A: "Yes, and we label it as such on screen and in the audit log. What is real is
    the normalisation - two deliberately incompatible schemas - and the seam
    where a live API plugs in. We would rather show you a real boundary than a
    fake integration."

Q: "Why not let the LLM explain its reasoning?"
A: "Because then the explanation and the decision come from different places,
    and a plausible explanation of a wrong number is the worst possible
    outcome. Our explanation IS the arithmetic - every term is on screen if you
    open it."

Q: "Isn't this just a filter and a sort?"
A: "The ranking is deliberately simple - about sixty lines - because it has to
    be defensible. The hard parts are everywhere else: knowing where the agent's
    authority ends, what to escalate, what NOT to escalate, and proving after
    the fact that it stayed inside its limits."

Q: "What breaks first if you scale this?"
A: "Real vendor integrations - auth, pagination, rate limits, and vendors whose
    stock figure lies. Our stage 6 re-validation exists because we assume the
    catalog is already out of date by the time we act on it."


8.8.11  THE TRAP: OUR AUDIT TRAIL CLAIMED A HUMAN APPROVED WHAT NOBODY SAW
    Our whole pitch is that the record can be trusted. So the closing entry has
    a field, approved_by_human, and it answered by looking for any decision in
    the trail with the actor USER. That reads as obviously correct. It was
    wrong, and it was wrong on the demo path.

    A furniture order sits inside the authorisation limit deliberately, so the
    agent proceeds alone - that is the beat where we show the boundary working.
    But furniture also triggers the usage-context question, and the buyer's
    answer to it is recorded as a USER decision too. Because it is theirs. So
    the close found a USER decision, concluded a person had signed, and wrote
    "after human approval" into the finance record for a purchase no person ever
    saw.

    Naive: infer authorisation from the actor. Every USER entry looks like
    consent when you are only looking at who wrote it.

    What we do: ask WHERE the decision was made, not merely who made it. A USER
    decision at stage 2 is a preference. Only a USER decision at the
    authorisation gate is somebody taking the purchase on themselves. Two tests
    hold both directions, because a fix that always answers "no" passes the
    first one.

    THE LINE:   "The dangerous bug in an audit trail is not the one that
                 crashes. It is the one that produces a confident, readable,
                 well-formatted sentence that is not true - and ours said a
                 human had approved something no human had seen."


8.8.12  THE TRAP: TWO ORDERS QUIETLY BECAME ONE TRANSACTION
    We promise that one transaction id replays a whole order in sequence. The
    id was four random digits, and the log was opened in append mode. Both
    choices are individually reasonable. Together they mean a repeat id does not
    fail - it appends a second order into the first one's file. Replay then
    returns two interleaved runs, and the entry numbering restarts from 01
    halfway down.

    We did not reason our way to this. We found it: 1,337 files in exports/
    against 9,000 possible ids, and 39 of them holding duplicate entry numbers.
    One file had two complete orders seven seconds apart.

    Naive: switch to a UUID. That fixes it and costs the thing the short id was
    for - a judge being able to read TXN-4471 off the screen and say it out
    loud.

    What we do: keep four digits, and check the directory before handing one
    out. The id stays readable; the guarantee stops depending on luck. And the
    first write uses "x" rather than "a", so a collision that somehow survives
    that fails loudly instead of corrupting the record we are presenting as
    evidence.

    THE LINE:   "Append mode is how a log that cannot lose data ends up merging
                 two stories into one. We would rather the write fail in front
                 of you than the file read cleanly and be wrong."


8.8.13  THE TRAP: THE TEST GUARDING OUR SCREEN MEASURED THE WRONG SCREEN
    We have a test that fails if pipeline vocabulary reaches the default
    surface, because Meena has never heard of stage 4. It passed. The screen was
    printing "act_now", "hard constraints", "6 source(s)" and "structured
    requirements using the offline parser" the whole time.

    Two holes, both invisible. It collected paragraphs and captions only - so
    expander and button LABELS, which are visible while the drill-down is shut,
    were never checked, and that is exactly where the leaks were. And it claimed
    to exclude drill-down contents while doing no such thing: Streamlit's test
    harness flattens the tree, so every word inside every breakdown counted as
    surface. That second hole is why nobody could add a banned word to the list
    without the drill-downs failing - the guard had been quietly load-bearing in
    the wrong direction.

    Naive: trust a green test. A test that measures the wrong thing is worse
    than no test, because it buys silence.

    What we do: subtract drill-down contents by identity, add the labels, and
    run it on the closed order as well as the approval screen. Then fix what it
    finds. The reasoning did not get deleted - it is the product. It stopped
    naming which module produced it.

    THE LINE:   "Our product bar test was green while the screen said 'act_now'.
                 We had written the assertion and never checked what it could
                 see."


8.8.14  THE TRAP: WE REVERSED FOUR OF OUR OWN DESIGN RULES AND LEFT THE
        ARGUMENT AGAINST THEM SITTING IN THE FILE
    ui/theme.py carried written rules banning shadows, hover states on static
    tiles, and pill-shaped tags, each with a reason we could defend out loud. We
    then decided to go the other way on all of them - glass panels, lift under
    the cursor, pills everywhere.

    The trap is not the reversal. It is that a reversal is two jobs and only the
    first one is fun. Change the CSS and you are done in twenty minutes; the
    paragraph explaining why shadows are wrong is still sitting directly above
    the shadow, and now the repo argues with itself. A judge who opens that file
    finds either a rule we broke or a comment we never read. Both are worse than
    whichever choice we made.

    Naive: delete the old comments. That loses the thinking, which is the part
    worth having.

    What we do: rewrite each rule to say what the code now does AND what the
    original concern was, because the concern was right and it is what keeps the
    new version honest. "Never a shadow" became "a hairline says where a panel
    STOPS, depth says a panel is a separate OBJECT" - two jobs, two devices, and
    the border did not go anywhere when the shadow arrived. "No hover on static
    tiles" became "the cursor is the affordance, not the lift", with
    cursor:default set on every tile that is not a button.

    THE LINE:   "We changed our minds about four things and rewrote the reasons
                 to match. A file that argues with its own code has told you
                 nobody read it since."


8.8.15  THE TRAP: THE PRETTIEST EFFECT WE ADDED WAS THE ONE THE DEMO LAPTOP
        COULD NOT DRAW
    Glass panels want backdrop-filter, so we put one on the recommendation and
    the sidebar. Twice during ordinary use the renderer went unresponsive for
    tens of seconds - once mid-scroll, once just after approval. On the laptop
    we are presenting from: Intel UHD 620, 1.5x scaling, compositing a blur
    behind a full-height sidebar every frame.

    There was a second, quieter version of the same mistake underneath it. The
    page background had `background-attachment: fixed`, which sounds free. It
    was not doing anything at all - Streamlit scrolls an inner container, not the
    page, so there was nothing for `fixed` to hold still - while forcing all six
    background layers to repaint under every translucent panel on every scroll
    frame. Full price, no effect.

    Naive: keep the blur because glassmorphism is the look, and hope the room's
    machine is faster. Or panic and strip the whole design back to flat panels.

    What we do: ask what the blur was actually buying. A blur needs detail
    behind it to smear, and behind ours is near-black canvas with soft gradients
    and a 3%-opacity grid - there is nothing there to soften. The glass read was
    always coming from the other three properties: a translucent fill that lets
    the grid show through the panel, a highlight on the top edge, a shadow
    underneath. So the blur came out and the design did not change.

    Being straight about the evidence: that is two reproductions of a stall, not
    a benchmark. We tried to measure the frame rate and the harness we wrote for
    it stalled the page by itself, which says the machine is near its limit but
    does not give us a number. The claim in the comment is the small one.

    THE LINE:   "We took the blur out after the renderer hung twice on this
                 laptop. It cost us nothing, because on a near-black page there
                 was never anything behind the panel to blur."


8.8.16  THE TRAP: THE TEST GUARDING OUR CODE REFERENCES PASSED WHILE TWO OF
        THEM POINTED AT PROSE
    EFFICIENCY.md promises we can open the code the moment a judge asks, and a
    test checks every `file.py:N` in it exists and is not blank or a comment.
    The interface work shifted a few hundred lines around. Two references
    drifted. The test stayed green.

    One had slid off `_language_switch()` into the middle of that function's own
    docstring. The other had landed on a lone closing triple-quote 160 lines
    from `buyer_reviews()`, the function it names. Both are "a line of real
    code" to a check that only asks whether the line is empty.

    Naive: fix the two numbers. The same thing happens on the next refactor, and
    this is the SECOND time these references have rotted - the test exists
    because twelve of sixteen had drifted once already.

    What we do: fix the numbers, then make the guard catch this specific shape.
    EFFICIENCY.md cites things a judge can OPEN - a def, a call, a branch. It
    never cites a sentence. So a reference landing inside a string literal is
    always drift, and that is now its own test, parsed off the AST rather than
    guessed at with a regex. We checked it fails on both old numbers before
    trusting it.

    THE LINE:   "The guard was green while two references pointed at prose. A
                 test that only asks 'is this line blank' is a test that buys
                 silence."


8.8.17  THE TRAP: THE BACKGROUND WE WERE ASKED TO ADD WAS ALREADY THERE, BEING
        PAINTED WHERE NOBODY COULD SEE IT
    The page read as flat black and looked unfinished under the panels. The
    obvious response is to design a background: pick a gradient, put it on the
    page, done in five minutes.

    We went and read the stylesheet first, and the background was already in it
    - five layers on `.stApp`, a brand pool, a slate pool, a vignette and a 48px
    grid, all written months earlier and all invisible. Two separate reasons,
    and only one of them was ours:

    Ours: the opacities were below the floor at which an eye registers anything.
    The brand pool was the accent at 4% over a near-black page, which is a
    change of two or three values per channel. Real in the file, invisible on a
    screen. We had reviewed those numbers as CSS and never as light.

    Streamlit's: it puts a header bar across the top of the page, absolutely
    positioned, and paints it in the page colour unless it happens to be empty.
    `toolbarMode = "viewer"` keeps the options menu, so ours had content, so it
    was opaque - a solid rectangle sitting over exactly the band where the brand
    pool blooms. The pool was being rendered and then covered. Nothing in our
    code was wrong; a default in somebody else's was in the way.

    Naive: add a second background on top of the first. Now there are two
    definitions of the page, they disagree, and the next person to touch it has
    to work out which one is live.

    What we do: find out why the first one is invisible, fix both causes, and
    change nothing else. Two token values, one gradient position, one rule for
    the header. Every panel, chart and chip on all four screens is untouched.

    The header fix has its own small trap, and we only found it by scrolling.
    Fully transparent is the obvious answer and it looks right at rest - then
    the page slides underneath the bar that does not move, and the top row of
    whatever you are reading gets sliced in half at the frame with the menu
    button hovering beside the offcut. So the bar keeps a background: the page
    colour fading out rather than a solid block. Scrolled content dissolves
    upward instead of being guillotined, and the pool still blooms underneath.

    THE LINE:   "The gradient was already in the file. It was being drawn at 4%
                 on a black page and then covered by a toolbar we did not know
                 was opaque. We found that out before writing a second one."


8.8.18  THE TRAP: WE REQUIRED AN ANSWER AND ACCEPTED ONLY ONE SHAPE OF IT,
        WITHOUT EVER SAYING WHAT THAT SHAPE WAS
    The agent would not start without a delivery deadline. It asked for one
    politely - "Before I start looking, your delivery deadline in days?" - and
    the only reply it could actually read was a digit followed by the word
    "days". "Two weeks" failed. "A month" failed. "No rush" failed. And because
    a reply is appended to the brief so far and the whole thing is re-checked,
    the same question came back every time, forever. The most reasonable answer
    a buyer can give - "I have no deadline" - was the one answer the system
    treated as silence.

    Naive: widen the regex until it stops embarrassing us. That fixes the
    typing and leaves the real hole, which is that a required field had no way
    to hold "there is no requirement". The model said `max_delivery_days: int =
    Field(gt=0)`. Not optional. A brief without a deadline could not be
    constructed at all - the scope gate was the only thing standing between us
    and a ValidationError, and nobody had noticed it was doing that job.

    What we do: make "no deadline" a value the system can hold, and keep the
    question. `None` on that field now means one specific thing - the buyer
    told us there is no deadline - and never "we forgot to ask", which is
    exactly what the gate still being there guarantees. Then the same seam the
    price cap already had: stage 3 does not enforce a limit the buyer never
    set, stage 4 still ranks delivery, and the audit note says out loud that
    nothing was rejected on lead time.

    We also refused two tempting additions. "ASAP" is not a number; any value we
    picked would be our opinion printed back as the buyer's own HARD constraint,
    on the one field where inventing a number does the most damage. Calendar
    dates ("by 30 August") would make the same sentence parse to a different
    window tomorrow, which breaks the property the whole project is built on.

    THE LINE:   "The field could not hold 'no deadline', so the gate asking for
                 one was load-bearing - it was the only thing stopping a crash.
                 We made the absence representable, then kept the question."


8.8.19  THE TRAP: THE ONE-LINE FIX THAT WOULD HAVE RANKED THE SLOWEST SUPPLIER
        FIRST AND LOOKED FINE DOING IT
    With no deadline there is no cap to measure a margin against, so delivery
    has to fall back to the other method we already have: min-max across the
    surviving pool. That is a one-line change - add "delivery" to the min-max
    list - and it is wrong.

    Min-max is written for criteria where MORE is better. A higher rating is
    better; a longer replacement window is better. Delivery is days, and fewer
    is better. Handed the raw fraction, the slowest supplier in the pool scores
    1.0 on delivery and the fastest scores 0.0.

    What makes it dangerous is that nothing looks wrong. Every number is still
    between 0 and 1. The contributions still sum to the score. The bars still
    render. The winner is simply the wrong product, for a reason no one reading
    the screen can see - and our golden test does not catch it, because the demo
    brief states a ten-day window and never takes this path at all.

    What we do: an explicit `lower_is_better` flag through the normaliser, and a
    test that asserts the DIRECTION rather than the numbers - fastest in pool
    scores 1.0, slowest scores 0.0. We broke the inversion on purpose and
    confirmed that test, and only that test, went red.

    THE LINE:   "Adding delivery to the min-max list is one line and it silently
                 ranks the slowest supplier first. The golden test stays green
                 through it. We wrote the test that does not."


8.8.20  THE TRAP: A SIDEBAR OF PAST ORDERS THAT NOBODY EVER PLACED
    An account block and a list of past orders is what makes a build read as a
    product rather than a demo, and it is also the easiest thing in the whole
    app to fake. Four plausible rows - an item, a total, a date - and the panel
    looks lived-in on the first screenshot.

    We are the project whose entire claim is that the record can be trusted. A
    fabricated order in a list that links to an audit trail is the one lie this
    product cannot survive telling, and it is a lie a judge finds by clicking.

    What the obvious build does: hardcode three or four past orders, and either
    make the rows inert or link them all to the same sample log.

    What we do: the list holds only orders THIS session actually ran, and it
    holds the transaction context and its logger - the live objects - not a
    summary of them. Clicking a row calls the same render function the live
    screen calls, so a reopened order cannot show a figure the order never had.
    Nothing is written to disk on the list's account; the JSONL export was
    already written as each event happened. Close the app and the list is gone,
    because a session's memory is not a database and we are not pretending it is.

    An order that was DECLINED gets a row too, saying nothing was bought. A list
    that only shows purchases quietly loses every run where the answer was no,
    and those are the runs worth being able to point at.

    THE LINE:   "Every row in that list is an order this session actually placed.
                 We could have hardcoded four and looked established - but the
                 one thing we cannot fake is the record."


8.8.21  THE TRAP: STREAMLIT CANNOT SELECT A TAB, SO THE FEATURE QUIETLY
        BECOMES A WORSE FEATURE
    "Clicking a past order takes you to its audit log" runs straight into a
    Streamlit limit: `st.tabs` has no programmatic selection. There is no
    supported way to say "now show the Activity tab".

    The tempting workarounds are all worse than the problem. Rebuild the tab
    strip as a radio group so we can set it - a refactor of every screen, on a
    demo path we said was frozen. Or drop the click and let the sidebar be
    decoration.

    What we do: a past order REPLACES the four screens instead of borrowing one,
    with a Back button. That is not a workaround dressed up - it is the better
    interaction. The four tabs are about the order in progress; a finished order
    is a different subject, and showing it inside them would leave three tabs
    displaying somebody else's numbers. Every order-list-to-order-detail screen
    in every commerce tool works exactly this way.

    THE LINE:   "The framework could not switch tabs for us, so we asked whether
                 it should. A finished order is a different subject from the one
                 in progress - it gets its own screen and a way back."


8.8.22  THE TRAP: A LOGO IS A PICTURE, AND AN INTERFACE NEEDS A MARK
    The logo we were handed is a 1024x1024 JPEG: the glyph, the word EVETS
    under it, a navy background, and about sixty percent empty canvas. It is a
    good logo. It is not a usable interface asset, and the three reasons are
    each invisible until you look.

    The navy is opaque, and our page is #0a0b0e while our sidebar is #131316 -
    so one tile is wrong against both surfaces, in two different directions.
    The wordmark is baked in, and the header already writes "Evets" as text
    beside the mark, so the whole picture prints the product name twice. And
    the glyph occupies barely a third of the file, so shrinking the square to
    the 32 pixels the header allows lands the actual mark at about twelve.

    What the obvious build does: st.image("assets/logo.jpeg", width=40) in the
    header. It takes one line, it "works", and it ships a navy tile with the
    name written twice - re-read from disk on every click, because Streamlit
    re-runs the file top to bottom every time anyone presses anything.

    What we do: derive the mark from the logo. tools/make_logo_mark.py crops to
    the glyph's measured bounding box, turns the navy into real transparency,
    and repaints the glyph flat mint so no navy bleeds into the soft edges. It
    runs once, by hand, and its output is committed. The app reads that file a
    single time at import.

    Two details we would defend if asked. The mark keeps the logo's mint even
    though our accent is violet - a brand mark is the one element on a screen
    whose entire job is to be recognised, so it keeps the colour it was drawn
    in, and it sits on no plate, because mint on violet is two brand colours
    fighting inside 32 pixels. And the generator is a checked-in file rather
    than something someone did once in a notebook: "where did this asset come
    from?" should have a file for an answer. That is the same rule we hold the
    price history to.

    THE LINE:   "The logo goes in the header, the sidebar signature and the
                 browser tab - and nowhere else. A mark you see once is
                 branding; a mark you see on all four screens is a watermark."
